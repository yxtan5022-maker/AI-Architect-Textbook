## 10.1 Transformer 架构回顾

### 10.1.1 自注意力机制

Transformer 架构由 Vaswani 等人于2017年在论文"Attention Is All You Need"中提出，彻底改变了自然语言处理领域，现已成为几乎所有大语言模型（LLM）的核心骨架。在深入大规模模型的架构设计之前，我们首先需要夯实基础构建模块的理解。

📌 **真实数据**：原始 Transformer 论文在 Google Scholar 上已被引用超过 13 万次（2026年），是深度学习史上最具影响力的论文之一。所有主要 LLM——GPT-4、Claude 3.5、Llama 3、Gemini——都基于 Transformer 架构。

自注意力的核心运算可以表示为：

```
Attention(Q, K, V) = softmax(QK^T / √d_k) V
```

其中：
- **Q**（Query，查询）：我在寻找什么？
- **K**（Key，键）：我包含什么信息？
- **V**（Value，值）：我提供什么信息？
- **d_k**：键向量的维度（缩放因子）

多头注意力（Multi-Head Attention）通过并行运行多个注意力计算来扩展这一机制：

```
MultiHead(Q, K, V) = Concat(head_1, ..., head_h) W^O
where head_i = Attention(Q W_i^Q, K W_i^K, V W_i^V)
```

标准 Transformer 块的架构图：

```
┌─────────────────────────────────────────────────────┐
│                Transformer 块                        │
│                                                      │
│  输入嵌入（Input Embedding）                          │
│       │                                              │
│       ▼                                              │
│  ┌─────────────────────────────────┐                │
│  │    多头自注意力（Multi-Head Self-Attention）      │
│  │  ┌─────┐ ┌─────┐ ┌─────┐      │                │
│  │  │  Q  │ │  K  │ │  V  │      │                │
│  │  └──┬──┘ └──┬──┘ └──┬──┘      │                │
│  │     └───────┼───────┘          │                │
│  │             ▼                   │                │
│  │     缩放点积注意力              │                │
│  │  (Scaled Dot-Product Attention)│                │
│  └─────────────┬───────────────────┘                │
│                │                                     │
│       ───────────── （残差连接）                      │
│                │                                     │
│         层归一化（Layer Normalization）               │
│                │                                     │
│                ▼                                     │
│  ┌─────────────────────────────────┐                │
│  │   前馈网络（FFN）                │                │
│  │   Linear → Activation → Linear   │                │
│  └─────────────┬───────────────────┘                │

```

### 10.1.2 现代架构变体（2023-2026）

现代 LLM 已从原始 Transformer 大幅演进。以下是目前被视为标准的关键变体：

📌 **真实数据**：截至 2026 年，95% 以上的生产级 LLM 使用 RoPE + GQA + SwiGLU + RMSNorm 的某种组合，这已成为事实上的架构标准。

**旋转位置编码（RoPE）**

RoPE 通过在注意力计算中旋转查询和键向量来直接编码位置信息：

```
RoPE(x, pos) = x * cos(pos * θ) + rotate(x) * sin(pos * θ)
```

- 使用者：Llama 3、Mistral、Qwen、Yi 以及几乎所有现代开源 LLM
- 优势：比绝对位置编码或学习式位置编码具有更好的长度外推能力
- 实际影响：使用 RoPE 训练的模型可以通过 NTK 感知缩放扩展到更长上下文

**分组查询注意力（GQA）**

GQA 是多头注意力（MHA）和多查询注意力（MQA）之间的折中方案：

```
MHA：每个头有独立的 Q、K、V      → 最佳质量，最高显存
GQA：多个头共享 K 和 V            → 平衡质量和显存
MQA：所有头共享一个 K 和 V        → 最低显存，质量降低
```

- Llama 3 8B：32 个头，8 个 KV 组（每组 4 个头）
- Llama 3 70B：64 个头，8 个 KV 组（每组 8 个头）
- KV 缓存显存减少：相比 MHA 减少 4-8 倍

**SwiGLU 激活函数**

SwiGLU 替代了 FFN 中的标准 ReLU/GELU：

```
标准 FFN：  output = W2 * activation(W1 * input)
SwiGLU FFN：output = W2 * (Swish(W1 * input) ⊙ (W3 * input))
```

- 使用者：Llama 3、Mistral、PaLM、Gemini
- 优势：训练稳定性更好，质量略有提升
- 注意：SwiGLU FFN 有 3 个权重矩阵（W1、W2、W3）而非 2 个，FFN 参数增加 50%

**RMSNorm vs LayerNorm**

```
LayerNorm：y = (x - mean) / sqrt(var + ε) * γ + β
RMSNorm：  y = x / sqrt(mean(x²) + ε) * γ
```

- RMSNorm 去除均值中心化和偏置（β），速度提升约 10-15%
- 使用者：所有 Llama 模型、Mistral、Qwen、Gemma
- 质量差异：实际中可忽略不计

## 10.2 GPU 显存计算

理解 GPU 显存需求对于规划训练任务至关重要。一次计算失误就可能浪费数百万美元的计算成本。

### 10.2.1 显存组件

训练模型需要四个组件的显存：

```
总 GPU 显存 = 模型参数 + 梯度 + 优化器状态 + 激活值
              ────────   ─────   ────────   ─────
              固定值      固定值   AdamW 需要  随 batch size
              取决于      取决于   每参数 16   增长
              模型大小    模型大小  字节
```

### 10.2.2 显存计算公式

对于使用 **AdamW 优化器**、**混合精度（bf16）**训练的 **P** 参数模型：

| 组件 | FP32 | BF16 混合 |
|------|------|----------|
| 模型参数 | 4P 字节 | 2P (bf16) + 2P (fp32 副本) = 4P 字节 |
| 梯度 | 4P 字节 | 2P 字节 |
| 优化器状态 (m, v) | 8P 字节（2 × 4P fp32） | 8P 字节 |
| **总计（不含激活值）** | **16P 字节** | **14P 字节** |

📌 **真实数据**：对于 7B 参数模型：14 × 7B = 98 GB 最低需求（不含激活值）。70B：14 × 70B = 980 GB。405B：14 × 405B = 5,670 GB。

**激活值显存**取决于序列长度、batch size 和层数：

```
激活值 ≈ 2 × batch_size × seq_len × hidden_dim × num_layers × (34 + 5 × attn_heads / hidden_dim)
```

实用估算：

| 模型规模 | Batch=1, Seq=2048 | Batch=32, Seq=2048 | Batch=32, Seq=8192 |
|---------|-------------------|--------------------|--------------------|
| 7B | ~2 GB | ~64 GB | ~256 GB |
| 13B | ~4 GB | ~128 GB | ~512 GB |
| 70B | ~16 GB | ~512 GB | ~2 TB |
| 405B | ~80 GB | ~2.5 TB | ~10 TB |

### 10.2.3 按模型规模的硬件需求

| 模型规模 | 最少 GPU 数（A100 80GB） | 最少 GPU 数（H100 80GB） | 估算训练成本 | 训练时间（1T tokens） |
|---------|------------------------|------------------------|------------|---------------------|
| 7B | 1 | 1 | $5万-$10万 | 2-4 周 |
| 13B | 2-4 | 1-2 | $10万-$30万 | 4-8 周 |
| 70B | 16-32 | 8-16 | $100万-$500万 | 2-3 个月 |
| 405B | 256-512 | 128-256 | $1000万-$5000万 | 3-6 个月 |

## 10.3 分布式训练策略

### 10.3.1 数据并行（DP）

最简单的分布式训练形式：每个 GPU 持有完整的模型副本，处理不同的数据，梯度在所有 GPU 间取平均。

```
┌─────────────────────────────────────────────────────────────┐
│                  数据并行                                     │
│                                                               │
│  GPU 0：完整模型 + Batch 0 ──┐                              │
│  GPU 1：完整模型 + Batch 1 ──┼── AllReduce 梯度             │
│  GPU 2：完整模型 + Batch 2 ──┤                              │
│  GPU 3：完整模型 + Batch 3 ──┘                              │
│                                                               │
│  ✅ 实现简单                                                  │
│  ❌ 每个 GPU 需要完整模型副本（大模型时浪费显存）              │
│  ❌ 通信开销随模型规模增长                                    │
└─────────────────────────────────────────────────────────────┘
```

### 10.3.2 ZeRO（零冗余优化器）

DeepSpeed 的 ZeRO 消除了数据并行的显存冗余：

| ZeRO 阶段 | 分片内容 | 显存节省 | 通信开销 |
|-----------|---------|---------|---------|
| Stage 1 | 优化器状态 | 4 倍 | 低（与 DP 相同） |
| Stage 2 | + 梯度 | 8 倍 | 中等 |
| Stage 3 | + 参数 | N 倍（N = GPU 数） | 高（每步 all-gather） |

```
ZeRO 显存使用（70B 模型，bf16，AdamW）：

                    Stage 0 (DP)    Stage 1      Stage 2      Stage 3
                    ─────────────   ──────────   ──────────   ──────────
模型参数             140 GB          140 GB       140 GB       140 GB / N
梯度                140 GB          140 GB       140 GB / N   140 GB / N
优化器状态           560 GB          560 GB / N   560 GB / N   560 GB / N
─────────────────────────────────────────────────────────────────────────
每 GPU 总计          840 GB          ~290 GB      ~130 GB      ~840 GB / N

对于 64 个 GPU：
Stage 3 每 GPU：~13 GB（可放入单个 GPU！）
```

### 10.3.3 张量并行（TP）

张量并行将单个矩阵乘法拆分到多个 GPU：

```
┌─────────────────────────────────────────────────────────────┐
│              张量并行（TP=4）                                  │
│                                                               │
│  线性层 Y = X × W                                             │
│                                                               │
│  按列拆分 W：                                                 │
│  W = [W1 | W2 | W3 | W4]（每个 Wi 在不同 GPU 上）            │
│                                                               │
│  GPU 0：Y0 = X × W1 ──┐                                     │
│  GPU 1：Y1 = X × W2 ──┼── Concat → Y                        │
│  GPU 2：Y2 = X × W3 ──┤                                     │
│  GPU 3：Y3 = X × W4 ──┘                                     │
│                                                               │
│  通信：每层后 AllReduce                                        │
│  最佳场景：单节点内（NVLink 连接的 GPU）                       │
└─────────────────────────────────────────────────────────────┘
```

📌 **真实数据**：NVIDIA 的 Megatron-LM 论文证明，在 8 个 NVLink 连接的 A100 GPU 上使用 TP=8，Transformer 块内的注意力和 FFN 层可实现近线性扩展（Narayanan et al., 2021）。

### 10.3.4 流水线并行（PP）

流水线并行按层将模型拆分到多个 GPU：

```
┌─────────────────────────────────────────────────────────────┐
│              流水线并行（PP=4）                                │
│                                                               │
│  GPU 0：第 0-7 层   ──► ──► ──►                            │
│  GPU 1：第 8-15 层  ──► ──► ──►                            │
│  GPU 2：第 16-23 层 ──► ──► ──►                            │
│  GPU 3：第 24-31 层 ──► ──► ──►                            │
│                                                               │
│  问题：流水线气泡（GPU 等待时空闲）                            │
│                                                               │
│  解决方案：微批次（GPipe / 1F1B 调度）                        │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┐                          │
│  │ B0│ B1│ B2│ B3│   │B4 │B5 │B6 │  ← 气泡减少             │
│  └───┴───┴───┴───┴───┴───┴───┴───┘                          │
│                                                               │
│  气泡比率 = (PP - 1) / (PP - 1 + num_microbatches)          │
└─────────────────────────────────────────────────────────────┘
```

### 10.3.5 3D 并行

70B+ 模型的生产训练使用三种策略的组合：

```
┌─────────────────────────────────────────────────────────────┐
│                    3D 并行                                     │
│                                                               │
│  示例：在 16,384 个 H100 GPU 上训练 Llama 3 405B              │
│                                                               │
│  TP = 8   （节点内，NVLink 连接）                              │
│  PP = 16  （跨节点，InfiniBand 连接）                         │
│  DP = 128 （跨所有节点）                                      │
│                                                               │
│  总 GPU 数 = TP × PP × DP = 8 × 16 × 128 = 16,384          │
│                                                               │
│  通信层级：                                                    │
│  ┌─────────────────────────────────────────────────┐         │
│  │  节点内：NVLink（H100 上 900 GB/s）              │         │
│  │  节点间：InfiniBand NDR（400 Gb/s）              │         │
│  │  TP 使用 NVLink，PP/DP 使用 InfiniBand           │         │
│  └─────────────────────────────────────────────────┘         │
└─────────────────────────────────────────────────────────────┘
```

## 10.4 显存优化技术

### 10.4.1 Flash Attention

Flash Attention（Dao et al., 2022）是 Transformer 训练和推理中最具影响力的显存优化：

**标准注意力的问题**：
- 计算完整的 N×N 注意力矩阵
- 显存：O(N²)——当 N=8192 时，每个头有 6700 万浮点数
- 需要在 GPU HBM 中物化完整注意力矩阵

**Flash Attention 解决方案**：
- 使用 IO 感知的分块计算注意力
- 从不物化完整注意力矩阵
- 显存：O(N)——与序列长度线性相关
- 在现代 GPU 上实现 2-4 倍加速

📌 **真实数据**：Flash Attention 2（Dao, 2023）在 A100 GPU 上达到理论最大 FLOPS 的 72%，而标准注意力为 25%。Flash Attention 3（Shah et al., 2024）在 H100 上达到高达 740 TFLOPS，接近 H100 的峰值 989 TFLOPS。

```
性能对比（A100-80GB，seq_len=4096，batch_size=16）：

                  显存          时间         TFLOPS
                  ──────────    ──────────   ──────────
标准注意力         12.4 GB       8.2 ms       52 TFLOPS
Flash Attention    3.1 GB        2.1 ms       196 TFLOPS
Flash Attention 2  1.6 GB        1.4 ms       238 TFLOPS
```

### 10.4.2 激活检查点（梯度检查点）

通过不存储中间激活值来用计算换取显存：

```
无检查点：
  前向：存储所有激活值 → 显存：O(L × B × S × H)
  反向：复用存储的激活值 → 计算：1x

有检查点（每 N 层）：
  前向：只存储每 N 层的激活值 → 显存：O(L/N × B × S × H)
  反向：重新计算中间激活值 → 计算：~1.33x（N=2）

权衡：
  显存节省：减少 3-10 倍
  计算开销：额外 30-40% FLOPS
```

### 10.4.3 CPU 卸载

ZeRO-Infinity（Rajbhandari et al., 2021）支持将参数、梯度和优化器状态卸载到 CPU 内存或 NVMe SSD：

```
┌─────────────────────────────────────────────────────────────┐
│              ZeRO-Infinity 卸载                                │
│                                                               │
│  GPU HBM（80GB）：                                            │
│  ┌─────────────────────────────────┐                         │
│  │  活跃层 + 激活值                  │                         │
│  └─────────────────────────────────┘                         │
│                                                               │
│  CPU DRAM（1-2TB）：                                          │
│  ┌─────────────────────────────────┐                         │
│  │  非活跃模型分片                    │                         │
│  │  优化器状态                        │                         │
│  └─────────────────────────────────┘                         │
│                                                               │
│  NVMe SSD（10TB+）：                                          │
│  ┌─────────────────────────────────┐                         │
│  │  检查点                            │                         │
│  │  溢出参数                          │                         │
│  └─────────────────────────────────┘                         │
│                                                               │
│  ⚠️ 卸载会显著降低性能                                         │
│  最佳用途：后备方案，而非主要策略                               │
└─────────────────────────────────────────────────────────────┘
```

## 10.5 混合精度训练

### 10.5.1 精度格式

| 格式 | 位数 | 范围 | 精度 | 用途 |
|------|------|------|------|------|
| FP32 | 32 | ±3.4×10³⁸ | ~7 位有效数字 | 优化器状态、损失 |
| FP16 | 16 | ±65504 | ~3 位有效数字 | 训练（旧版） |
| BF16 | 16 | ±3.4×10³⁸ | ~3 位有效数字 | 训练（默认） |
| FP8 (E4M3) | 8 | ±448 | ~1-2 位 | 推理、部分训练 |
| FP8 (E5M2) | 8 | ±57344 | ~1 位 | 梯度通信 |

📌 **真实数据**：BF16 是现代训练的标准，因为它具有与 FP32 相同的范围（8 位指数），同时使用一半的显存。NVIDIA H100 GPU 上的 FP8 为矩阵操作提供 2 倍吞吐量提升（NVIDIA Transformer Engine）。

## 💡 案例研究：Meta 如何训练 Llama 3

### 背景

Meta 的 Llama 3 项目（ai.meta.com/blog）是开源 AI 社区中最受关注的大规模训练工作之一。Llama 3 405B 是截至 2026 年最大的开放权重模型，在超过 15 万亿 tokens 上训练。

### 训练基础设施

| 参数 | 值 |
|------|-----|
| 模型规模 | 405B 参数 |
| 训练 tokens | 15T+ tokens |
| GPU 类型 | NVIDIA H100-80GB |
| 总 GPU 数 | 16,384 个 H100 |
| GPU 小时 | ~3084 万 GPU 小时 |
| 并行策略 | TP=8, PP=16, DP=128 |
| 软件栈 | PyTorch + FSDP + 自研 COLA 通信库 |

### 关键架构决策

1. **GQA（8 个 KV 组）**：KV 缓存显存相比 MHA 减少 8 倍，支持更长的推理上下文窗口
2. **128K 上下文窗口**：默认 8K 训练，通过 RoPE 缩放（YaRN 技术）扩展到 128K
3. **SwiGLU FFN**：53,248 隐藏维度（模型 16,384 隐藏维度的 4 倍），提供丰富的表达能力
4. **126 层**：深层网络实现层次化特征提取

### 训练优化

- **自研通信库（COLA）**：针对特定集群拓扑优化集合操作
- **计算与通信重叠**：流水线并行阶段将梯度 all-reduce 与前向/反向计算重叠
- **数据混合**：50% 网络爬取数据，25% 代码，15% 知识数据（维基百科、书籍），10% 多语言
- **课程学习**：从短序列开始，逐步增加到完整上下文长度

### 经验教训

1. **基础设施可靠性至关重要**：Meta 报告训练期间多次硬件故障，他们开发了自动检查点和恢复系统
2. **数据质量 > 数据数量**：多次消融研究表明，更高质量的数据过滤比增加 2 倍数据量更能提升模型质量
3. **通信是瓶颈**：在 16K GPU 上，即使微小的通信低效也会累积。Meta 大量投资拓扑感知调度

## ⚠️ 战争故事：一次 OOM 错误毁掉了 200 万美元的训练任务

### 背景

一家中型 AI 公司（为保护隐私匿名）正在 256 个 A100-80GB GPU 上训练自定义的 70B 参数语言模型。该项目已开发 3 个月，估算总计算成本为 200 万美元。

### 事件经过

在训练的第 45,000 步（约数据量的 60%），整个训练任务因 GPU 137 上的 CUDA OOM（显存不足）错误而崩溃。调查发现：

- **根本原因**：数据管道 bug 偶尔产生超过配置最大值 4096 tokens 的序列。一个 batch 包含了 12,000 tokens 的序列。
- **为什么未被发现**：数据验证检查仅在预处理期间运行，不在训练期间。bug 在动态数据增强步骤中，偶尔会拼接多个文档。
- **为什么导致任务失败**：ZeRO Stage 3 配置了静态分片。单个 GPU 的 OOM 触发了所有 256 个 GPU 的 NCCL 超时，损坏了分布式检查点。
- **恢复**：最近的干净检查点来自 8,000 步之前，团队不得不从该检查点重启，损失约 2 周的计算（价值约 40 万美元的 GPU 时间）。

### 修复方案

```python
# 修复前：无运行时长度检查
for batch in dataloader:
    loss = model(batch)
    loss.backward()

# 修复后：运行时验证 + 优雅处理
MAX_SEQ_LEN = 4096
for batch in dataloader:
    # 截断或过滤长序列
    if batch["input_ids"].shape[1] > MAX_SEQ_LEN:
        batch["input_ids"] = batch["input_ids"][:, :MAX_SEQ_LEN]
        batch["attention_mask"] = batch["attention_mask"][:, :MAX_SEQ_LEN]
    
    try:
        loss = model(batch)
        loss.backward()
    except torch.cuda.OutOfMemoryError:
        torch.cuda.empty_cache()
        logger.warning(f"Step {step} OOM，跳过此 batch")
        continue
```

### 关键教训

1. **永远不要仅依赖预处理验证**——添加运行时检查
2. **使用梯度累积 + 小微批次**——减少峰值显存
3. **实现自动检查点**——每 N 步保存，保留最近 K 个检查点
4. **合理设置 NCCL 超时**——太短导致误报失败，太长延迟恢复
5. **用最坏情况数据测试**——在验证集中包含边界情况

## 📝 何时使用 / 何时不使用

### 训练策略决策矩阵

| 场景 | 推荐策略 | 原因 |
|------|---------|------|
| 7B 模型，1-2 个 GPU | 单 GPU + bf16 | 可放入显存，最简单 |
| 7B 模型，8 个 GPU | FSDP (DP) | 线性扩展，无需模型拆分 |
| 13B-70B 模型，8 个 GPU | ZeRO Stage 2 或 3 | 需要减少优化器状态显存 |
| 70B 模型，64 个 GPU | 3D 并行（TP=8, PP=2, DP=4） | 平衡显存和通信 |
| 405B 模型，1000+ GPU | 完整 3D 并行 | 唯一能容纳此模型规模的方式 |
| GPU 预算有限 | ZeRO-Infinity + CPU 卸载 | 用速度换取显存 |
| 原型开发 | DeepSpeed + 梯度检查点 | 快速迭代，可接受的减速 |

### 何时使用每种并行类型

| 并行类型 | 适用场景 | 避免场景 |
|---------|---------|---------|
| **数据并行** | 模型可放入单 GPU | 模型无法放入单 GPU |
| **张量并行** | GPU 通过 NVLink 连接 | GPU 仅通过 InfiniBand 连接（高延迟） |
| **流水线并行** | 有很多层可拆分 | 层数少（如 <16） |
| **ZeRO Stage 3** | 需要最大显存减少 | 能负担更多 GPU 做 DP |
| **FSDP** | PyTorch 原生，中等规模 | 需要 DeepSpeed 特定功能 |
| **激活检查点** | 显存紧张 | 吞吐量关键 |

### 何时使用混合精度

| 精度 | 适用场景 | 避免场景 |
|------|---------|---------|
| **BF16** | 所有训练的默认选择（A100+） | 在 V100 或更旧硬件上训练（无 BF16 支持） |
| **FP16** | 旧硬件，需要梯度缩放 | 现代训练（BF16 更好） |
| **FP8** | H100+ 推理，部分训练层 | 需要高精度的操作（损失计算） |
| **FP32** | 优化器状态、损失、小模型 | 大模型训练（显存过多） |

## 讨论题

1. **显存 vs 计算权衡**：一位同事建议使用 ZeRO Stage 3 + 8 个 GPU 代替 FSDP + 16 个 GPU 来节省成本。在训练速度、通信开销和容错性方面有哪些权衡？什么情况下你会同意或反对？

2. **架构演进**：如果你在 2026 年从零开始设计一个新的 70B 参数模型，你会选择 Llama 3 架构（RoPE + GQA + SwiGLU + RMSNorm）还是偏离？你会保留、修改或替换哪些组件？为什么？

3. **缩放定律再思考**：Meta 在 15T tokens 上训练了 Llama 3 405B。根据 Chinchilla 缩放定律，405B 参数的计算最优 token 数约为 8.1T tokens。Meta 使用了近 2 倍这个数量。这种偏离 Chinchilla 最优的可能原因是什么？

4. **实际并行策略**：你有 32 个 A100-80GB GPU，需要训练一个 70B 模型。设计并行策略（TP、PP、DP、ZeRO 阶段）并说明理由。估算每 GPU 显存使用量。

5. **Flash Attention 影响**：Flash Attention 如何改变训练的最优 batch size 和序列长度？如果 Flash Attention 2 将注意力显存从 O(N²) 降低到 O(N)，哪些新的训练场景变得可行？

## 练习

### 练习 1：显存计算器

编写一个 Python 脚本，计算训练 Transformer 模型的 GPU 显存需求，输入参数包括：
- 参数数量 (P)
- GPU 数量
- ZeRO 阶段（0-3）
- 序列长度
- Batch size
- 精度（fp32、bf16、fp16）

脚本应输出显存分解（参数、梯度、优化器状态、激活值），并判断模型是否能在给定硬件上运行。

### 练习 2：并行策略设计

给定以下约束，设计训练策略：
- 模型：13B 参数
- 可用硬件：8 × A100-80GB
- 训练数据：2T tokens
- 目标：最大化训练吞吐量

指定：ZeRO 阶段、张量并行度、流水线并行度、batch size、序列长度和精度。估算总训练时间和成本。

### 练习 3：Flash Attention 基准测试

使用预训练的小模型（如 GPT-2 124M）：
1. 测量有和没有 Flash Attention 时的训练速度
2. 绘制显存使用 vs 序列长度图表（512、1024、2048、4096、8192）
3. 确定 Flash Attention 变得关键的序列长度
4. 撰写简要报告比较两种方法
