## 6.1 MLOps 的定义与价值

### 6.1.1 什么是 MLOps？

🟢 **初级**

MLOps（机器学习运维）是一组将机器学习、DevOps 和数据工程相结合的实践，用于可靠高效地在生产环境中部署和维护 ML 系统。可以将其理解为连接可用的 Jupyter notebook 与生产级 ML 服务之间的桥梁。

```
传统 ML 工作流：
  数据 → 模型 → Notebook → ??? → 生产环境（也许）

MLOps 工作流：
  数据 → 模型 → 版本化 → 测试 → 部署 → 监控 → 重训练
       ↑                                        |
       └────────────────────────────────────────┘
```

**正式定义：**

> MLOps 是一门 ML 工程学科，专注于可靠、及时地在生产环境中部署和管理 ML 模型，涵盖从开发到监控和重训练的整个生命周期。

### 6.1.2 MLOps 的三大支柱

🟡 **中级**

MLOps 建立在三个基础支柱之上：

```
                    ┌─────────────────┐
                    │     MLOps       │
                    └────────┬────────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐
     │   自动化    │  │    集成     │  │    监控     │
     │ Automation │  │ Integration│  │ Monitoring │
     └────────────┘  └────────────┘  └────────────┘
```

| 支柱 | 描述 | 关键组件 |
|------|------|---------|
| **自动化** | 自动化重复性 ML 任务 | CI/CD 管道、自动训练、自动扩缩容 |
| **集成** | 将 ML 集成到软件工程实践中 | 版本控制、代码审查、测试框架 |
| **监控** | 持续监控模型和数据质量 | 漂移检测、性能指标、告警 |

### 6.1.3 为什么 MLOps 重要——商业论证

🔴 **高级**

这些统计数据令人警醒：

- **87%** 的 ML 模型从未进入生产环境（VentureBeat, 2023）
- **53%** 的公司报告在 ML 规模化方面遇到困难（Algorithmia）
- ML 模型在生产中故障的**平均成本**：每次事件 15 万至 50 万美元
- **部署时间**：没有 MLOps 需要 2-6 个月；有 MLOps 只需 1-2 周

```
没有 MLOps 的成本：
┌─────────────────────────────────────────────────────┐
│                                                     │
│  手动流程             ──►  更高的劳动力成本            │
│  没有版本控制          ──►  可复现性丧失               │
│  没有监控             ──►  静默故障                   │
│  没有自动化测试        ──►  质量退化                   │
│  没有 CI/CD           ──►  上市时间缓慢               │
│                                                     │
│  总影响：ML 系统的 TCO 高出 3-10 倍                   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

## 6.2 MLOps 成熟度模型（Level 0-3）

### 6.2.1 成熟度等级概述

🟡 **中级**

MLOps 成熟度模型最初由 Google Cloud 提出并经社区扩展，为评估和改进 ML 运营实践提供了框架。

```
成熟度等级概述：
╔═══════════╦══════════════════════════════════════════════════════╗
║  Level 0  ║  手动流程 (Manual Process)                           ║
║           ║  - 手动训练，手动部署                                  ║
║           ║  - 没有 CI/CD，没有监控                                ║
║           ║  - Jupyter notebook 即生产                            ║
╠═══════════╬══════════════════════════════════════════════════════╣
║  Level 1  ║  ML 管道自动化 (ML Pipeline Automation)               ║
║           ║  - 自动化训练管道                                      ║
║           ║  - 基础实验跟踪                                        ║
║           ║  - 简单部署自动化                                      ║
╠═══════════╬══════════════════════════════════════════════════════╣
║  Level 2  ║  ML 的 CI/CD (CI/CD for ML)                          ║
║           ║  - 完整 CI/CD 管道                                    ║
║           ║  - 自动化测试                                         ║
║           ║  - 基础设施即代码                                      ║
╠═══════════╬══════════════════════════════════════════════════════╣
║  Level 3  ║  完整 MLOps (Full MLOps)                             ║
║           ║  - 自动化重训练触发                                    ║
║           ║  - 完整可观测性                                        ║
║           ║  - 自愈系统                                           ║
╚═══════════╩══════════════════════════════════════════════════════╝
```

### 6.2.2 Level 0：手动流程

🟢 **初级**

**特征：**
- 基于脚本的手动训练
- 没有管道或自动化
- 模型手动部署（或不部署）
- 没有模型或数据版本控制
- 没有监控

```
Level 0 架构：
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  数据科学家  │     │  数据科学家  │     │  生产环境    │
│  获取数据    │────►│  在Notebook │────►│  也许...     │
│             │     │  中训练      │     │  手动部署    │
└─────────────┘     └─────────────┘     └─────────────┘
                            │
                            ▼
                    ┌─────────────┐
                    │  "在我的机器 │
                    │   上可以运行"│
                    └─────────────┘
```

**痛点：**
- 没有可复现性
- 单点故障（科学家本人）
- 部署周期长
- 没有质量门控
- 知识孤岛

### 6.2.3 Level 1：ML 管道自动化

🟡 **中级**

**特征：**
- 自动化训练管道（但不是 CI/CD）
- 实验跟踪到位
- 引入模型注册中心
- 基础模型验证
- 简单部署脚本

```
Level 1 架构：
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  数据管道    │────►│  训练管道    │────►│  模型注册中心 │
│  (自动化)    │     │  (定时调度)  │     │              │
└──────────────┘     └──────────────┘     └──────────────┘
                                                    │
                                                    ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  监控        │◄────│  部署        │◄────│  验证        │
│  (基础)      │     │  (脚本化)    │     │  (手动)      │
└──────────────┘     └──────────────┘     └──────────────┘
```

**关键工具：**
- 工作流编排器（Kubeflow Pipelines, Airflow）
- 实验跟踪（MLflow, Weights & Biases）
- 模型注册中心（MLflow Model Registry）

### 6.2.4 Level 2：ML 的 CI/CD

- 自动化测试（单元测试、集成测试、模型质量测试）
- 基础设施即代码
- 自动化模型验证门控
- 特征仓库集成
- A/B 测试能力

## 6.4 MLOps 与 DevOps 的关系

### 6.4.1 根本区别

🟡 **中级**

虽然 MLOps 建立在 DevOps 原则之上，但 ML 系统具有独特的特性，需要专门的实践：

```
DevOps vs MLOps 对比：
┌─────────────────┬───────────────────┬───────────────────────┐
│ 方面             │ DevOps            │ MLOps                 │
├─────────────────┼───────────────────┼───────────────────────┤
│ 主要产物         │ 应用代码          │ ML 模型 + 数据         │
│ 测试             │ 单元/集成测试      │ + 模型质量测试         │
│ 版本控制         │ 代码              │ + 数据 + 模型          │
│ 部署             │ 蓝绿部署          │ + 金丝雀 + 影子部署    │
│ 监控             │ 系统指标          │ + 数据/模型漂移        │
│ 反馈循环         │ 用户反馈          │ + 性能衰减             │
│ 依赖项           │ 代码库            │ + 数据 + 环境          │
│ 故障模式         │ 系统崩溃          │ 静默退化               │
└─────────────────┴───────────────────┴───────────────────────┘
```

### 6.4.2 ML 特有的挑战

🔴 **高级**

```python
# DevOps 关注点："代码能运行吗？"
# MLOps 关注点："模型在数据变化后还能工作吗？"

# 示例：模型性能随时间衰减
# 第1个月：准确率 = 0.95（模型部署）
# 第3个月：准确率 = 0.88（检测到数据漂移）
# 第6个月：准确率 = 0.72（触发重训练）
# 第6个月+：准确率 = 0.94（模型重训练后重新部署）

# 这种生命周期在传统软件中不存在！
```

**ML 特有的关键挑战：**

1. **数据依赖性**：模型依赖于数据质量和分布
2. **非确定性**：相同代码 + 相同数据 ≠ 相同模型（不同随机种子、GPU 状态）
3. **性能熵**：随着现实世界数据偏离，模型随时间退化
4. **资源密集**：训练需要大量计算资源
5. **调试复杂性**：调试"模型为什么出错"比"代码为什么崩溃"更难

### 6.4.3 MLOps 如何扩展 DevOps

🟡 **中级**

```
传统 DevOps 管道：
  代码 → 构建 → 测试 → 部署 → 监控

MLOps 管道（扩展）：
  代码 ─┐
        ├──► 构建 ──► 测试 ──► 部署 ──► 监控
  数据 ─┤                              │
        ├──► 训练 ──► 验证 ──────────┤
  配置 ┘                            │
                                    ▼
                              ┌──────────┐
                              │  重训练   │
                              │  触发     │
                              └──────────┘
```

### 6.4.4 CI/CD/CT 范式

🔴 **高级**

MLOps 引入了第三个 "C" —— **持续训练（Continuous Training）**：

| 管道 | 触发条件 | 关注点 | 工具 |
|------|---------|--------|------|
| **CI**（持续集成） | 代码变更 | 代码质量、单元测试 | GitHub Actions, Jenkins |
| **CD**（持续部署） | 模型通过审批 | 部署、集成测试 | ArgoCD, Spinnaker |
| **CT**（持续训练） | 数据/性能变化 | 模型重训练、验证 | Kubeflow, Airflow |

```
CI/CD/CT 集成：
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   Git Push ──► CI 管道 ──► 构建产物                          │
│                                     │                       │
│                                     ▼                       │
│                              模型注册中心                     │
│                                     │                       │
│                    ┌────────────────┤                       │
│                    ▼                ▼                        │
│              CD 管道        CT 管道                          │
│                    │                │                        │
│                    ▼                ▼                        │
│              部署            重训练                           │
│                    │                │                        │
│                    ▼                ▼                        │
│              生产环境 ──► 监控 ──► 数据漂移？                 │
│                                     │                       │
│                              是：触发 CT                     │
│                              否：继续监控                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.4.5 共享原则

🟢 **初级**

尽管存在差异，MLOps 继承了 DevOps 的核心原则：

| DevOps 原则 | MLOps 应用 |
|-------------|-----------|
| **基础设施即代码** | Kubeflow、Terraform 用于 ML 基础设施 |
| **版本控制** | Git 管理代码、DVC 管理数据、MLflow 管理模型 |
| **自动化测试** | 单元测试 + 数据验证 + 模型质量测试 |
| **持续集成** | 合并 ML 代码、管道定义、配置 |
| **持续交付** | 带质量门控的自动化模型部署 |
| **监控和日志** | 系统指标 + 数据漂移 + 模型性能 |
| **协作** | 跨职能团队（数据科学家 + 工程师） |

## 总结

**关键要点：**

1. **MLOps 不是可选的** —— 对于任何认真对待生产环境中 ML 的组织来说都是必需的
2. **从当前位置开始** —— 使用成熟度模型评估并逐步规划改进
3. **工具链很重要** —— 选择与成熟度水平匹配的工具，并随你一起成长
4. **MLOps 扩展了 DevOps** —— 它继承了 DevOps 原则，但增加了 ML 特有的关注点
5. **持续训练** 是关键差异点 —— ML 系统需要持续重训练
