## 11.1 推理挑战

### 11.1.1 训练 vs 推理：不同的问题

在生产环境中服务大语言模型面临与训练根本不同的挑战。训练优先考虑吞吐量而非延迟，而推理必须同时平衡两者：

| 需求 | 训练 | 推理 |
|------|------|------|
| **主要指标** | 吞吐量（tokens/sec） | 延迟（首 token 时间 + tokens/sec） |
| **Batch size** | 大（1024+） | 可变（1-1024） |
| **显存模式** | 稳态 | 动态（随上下文增长） |
| **精度** | bf16/fp16（混合） | fp16/bf16/int8/int4 |
| **优化目标** | FLOPS 利用率 | 显存带宽 + FLOPS |
| **GPU 利用率** | 60-90% | 5-40%（解码阶段） |

📌 **真实数据**：vLLM（github.com/vllm-project/vllm）拥有 91.2K GitHub stars、21.8K forks、2000+ 贡献者，每月 pip 下载量达 560 万+次。它支持 1000+ 模型架构和 600+ 硬件加速器。截至 2026 年，它是最受欢迎的开源 LLM 推理引擎。

### 11.1.2 为什么 LLM 推理是显存带宽受限的

```
┌──────────────────────────────────────────────────────────────┐
│           为什么 LLM 推理是显存带宽受限的                        │
│                                                                │
│  预填充阶段（处理输入 prompt）：                                  │
│  ┌────────────────────────────────────────────┐              │
│  │  计算密集型：                                │              │
│  │  所有 token 的矩阵乘法                        │              │
│  │  FLOPS：O(n² × d)，其中 n = seq_len          │              │
│  │  GPU 利用率：60-80%                          │              │
│  └────────────────────────────────────────────┘              │
│                                                                │
│  解码阶段（生成输出 token）：                                    │
│  ┌────────────────────────────────────────────┐              │
│  │  显存带宽受限：                               │              │
│  │  每个新 token 都需要加载所有模型参数            │              │
│  │  算术强度：每层 O(1)                          │              │
│  │  GPU 利用率：5-30%                           │              │
│  │                                             │              │
│  │  70B 模型在 H100 上：                         │              │
│  │  - 需加载参数：140 GB                        │              │
│  │  - H100 带宽：3.35 TB/s                      │              │
│  │  - 每 token 最小时间：~42ms                   │              │
│  │  - 理论最大 tokens/sec：~24                   │              │
│  └────────────────────────────────────────────┘              │
└──────────────────────────────────────────────────────────────┘
```

📌 **真实数据**：NVIDIA H100 GPU 拥有 3.35 TB/s 显存带宽和 989 TFLOPS 算力。对于 FP16 格式的 70B 模型（140GB），解码阶段的算术强度仅为 ~0.7 FLOPS/byte——远低于 GPU 的平衡点 ~300 FLOPS/byte。这意味着 GPU 99% 的时间都在等待显存，而非计算。

### 11.1.3 推理延迟组件

```
总延迟 = 首 token 时间（TTFT）+（输出 tokens × 每 token 时间）

TTFT = 预填充时间 = f(prompt_length, model_size, batch_size)
  - 计算密集型阶段
  - 无 Flash Attention 时随 prompt 长度二次增长
  - 典型值：70B 模型 1K token prompt 约 100-500ms

每 token 时间 = 解码时间 = f(model_size, hardware_bandwidth)
  - 显存带宽受限
  - 大致恒定，与输出长度无关
  - 典型值：H100 上 70B 模型约 30-50ms/token
```

### 11.2.2 vLLM 深入解析

vLLM 的核心创新是 **PagedAttention**，解决了 KV 缓存显存管理问题：

**问题**：传统推理引擎为每个请求的 KV 缓存分配连续 GPU 显存，导致：
- 内部碎片（预分配但未使用的显存）
- 外部碎片（已分配块之间的间隙）
- 典型工作负载中 60-80% 的 KV 缓存显存被浪费

**PagedAttention 解决方案**：
- 将 KV 缓存存储在非连续的"页"中（类似操作系统虚拟内存）
- 每页是固定大小的块（通常 16 个 token）
- 页面可以动态分配/释放
- 支持并行采样和 beam search 的高效显存共享

📌 **真实数据**：PagedAttention 将 KV 缓存显存浪费从 60-80% 减少到 4% 以下，相比朴素实现可在每个 GPU 上支持 2-4 倍并发请求（Kwon et al., 2023）。

```
┌──────────────────────────────────────────────────────────────┐
│                    PagedAttention                              │
│                                                                │
│  传统 KV 缓存：                                                │
│  ┌──────────────────────────────────────┐                    │
│  │ 请求 1：[████████░░░░░░░░░░░░░░░░░░]│  60% 浪费          │

│  │  页表：                               │                    │
│  │  请求 1：[P3][P7][P12]     （3 页）   │  < 4% 浪费        │
```

### 11.2.3 TensorRT-LLM

NVIDIA 的 TensorRT-LLM 专门针对 NVIDIA GPU 进行优化：

- **图优化**：算子融合、内核自动调优
- **FP8 支持**：H100/H200 上原生 FP8，吞吐量翻倍
- **In-flight batching**：带动态 KV 缓存的连续批处理
- **多 GPU**：使用自定义 NCCL 内核的张量并行

📌 **真实数据**：TensorRT-LLM 在 NVIDIA H100 GPU 上，大 batch size 时吞吐量比 vLLM 高 1.5-3 倍，但需要更多设置工作且仅支持 NVIDIA 硬件（NVIDIA TensorRT-LLM 基准测试，2024）。

### 11.2.4 SGLang

SGLang（github.com/sgl-project/sglang）专注于结构化生成和复杂 LLM 工作流：

- **RadixAttention**：多轮对话的前缀感知缓存
- **结构化输出**：原生 JSON schema 强制执行
- **压缩 FSM**：高效约束解码
- **批处理推理**：优化离线批处理

## 11.3 KV 缓存架构

### 11.3.1 什么是 KV 缓存？

在自回归生成过程中，每个新 token 需要对所有先前 token 进行注意力计算。KV 缓存存储预计算的 Key 和 Value 向量以避免冗余计算：

```
无 KV 缓存：
  Token 1：计算 K1, V1
  Token 2：重新计算 K1, V1；计算 K2, V2
  Token 3：重新计算 K1, V1, K2, V2；计算 K3, V3
  总计算量：O(n³)（n 个 token）

有 KV 缓存：
  Token 1：计算 K1, V1；存储到缓存
  Token 2：从缓存加载 K1, V1；计算 K2, V2；追加
  Token 3：从缓存加载 K1, V1, K2, V2；计算 K3, V3；追加
  总计算量：O(n²)（n 个 token）
```

### 11.3.2 KV 缓存显存计算

```
KV 缓存大小 = 2 × num_layers × num_kv_heads × head_dim × seq_len × bytes_per_element

Llama 3 70B（bf16）：
  层数：80
  KV 头数：8（GQA）
  头维度：128
  字节数：2（bf16）
  
  每 token KV 缓存：2 × 80 × 8 × 128 × 2 = 327,680 字节 = 320 KB
  每序列（4096 tokens）：320 KB × 4096 = 1.25 GB
  每序列（128K tokens）：320 KB × 128K = 40 GB
```

📌 **真实数据**：对于 128K 上下文的 70B 模型，单个请求的 KV 缓存可占用 40 GB——A100-80GB GPU 的一半。这就是为什么 KV 缓存优化对长上下文模型服务至关重要。

### 11.3.3 KV 缓存优化策略

| 策略 | 显存减少 | 质量影响 | 复杂度 |
|------|---------|---------|--------|
| **GQA**（分组查询注意力） | 4-8 倍 | 可忽略 | 低（架构变更） |
| **PagedAttention** | 2-4 倍（减少浪费） | 无 | 中等 |
| **KV 缓存量化** | 2-4 倍 | 轻微退化 | 中等 |
| **滑动窗口注意力** | 窗口大小线性 | 限制长程依赖 | 低 |
| **StreamingLLM** | 恒定显存 | 丢失旧上下文 | 低 |
| **前缀缓存** | 跨请求共享 | 无 | 中等 |

## 11.4 量化与蒸馏

### 11.4.1 量化方法

量化通过使用低精度表示来减小模型大小：

| 方法 | 位数 | 70B 大小 | 加速 | 质量损失 | 校准数据 |
|------|------|---------|------|---------|---------|
| FP16/BF16 | 16 | 140 GB | 1x（基线） | 无 | 无 |
| INT8 (RTN) | 8 | 70 GB | 1.5-2 倍 | 极小 | 无 |
| GPTQ | 4 | 35 GB | 2-3 倍 | 小 | 128 个样本 |
| AWQ | 4 | 35 GB | 2-3 倍 | 小 | 128 个样本 |
| GGUF (Q4_K_M) | ~4.5 | 32 GB | 2 倍 | 中等 | 无 |
| GGUF (Q2_K) | ~2.5 | 18 GB | 1.5 倍 | 显著 | 无 |

📌 **真实数据**：GPTQ 和 AWQ 对高达 70B 参数的模型实现近乎无损的 4 位量化。WikiText-2 上的困惑度退化通常 <0.5 点，对大多数应用不可感知（Frantar et al., 2022; Lin et al., 2024）。

### 11.4.2 GPTQ vs AWQ

```
┌──────────────────────────────────────────────────────────────┐
│                    GPTQ vs AWQ 对比                            │
│                                                                │
│  GPTQ（训练后量化）：                                           │
│  - 逐层量化权重                                                 │
│  - 使用 Hessian 信息进行最优量化                                │
│  - 需要校准数据（128-256 个样本）                               │
│  - INT4/INT3 更好                                               │
│  - 量化过程较慢                                                 │
│                                                                │
│  AWQ（激活感知权重量化）：                                       │
│  - 通过激活统计识别"显著"权重                                    │
│  - 保留关键权重的高精度                                          │
│  - 量化速度快于 GPTQ                                            │
│  - INT4 更好                                                    │
│  - 对校准数据选择更鲁棒                                         │
│                                                                │
│  建议：                                                         │
│  - 通用部署使用 AWQ（更快、更鲁棒）                              │

```

## 11.5 批处理策略

### 11.5.1 静态 vs 动态 vs 连续批处理

```
┌──────────────────────────────────────────────────────────────┐
│                    批处理策略                                    │
│                                                                │
│  静态批处理：                                                   │
│  ┌─────┬─────┬─────┬─────┐                                   │
│  │ Req │ Req │ Req │ Req │  所有请求必须完成才能开始下一批       │
│  │  1  │  2  │  3  │  4  │                                   │
│  └─────┴─────┴─────┴─────┘                                   │
│  问题：GPU 在等待最长请求时空闲                                  │
│                                                                │
│  连续批处理：                                                   │
│  ┌─────┬─────┬─────┬─────┐                                   │
│  │ Req │ Req │ Req │ Req │  步骤 1                             │
│  │  1  │  2  │  3  │  4  │                                   │
│  └─────┴─────┴─────┴─────┘                                   │
│  ┌─────┬─────┬─────┬─────┐                                   │
│  │ Req │ Req │ Req │ New │  步骤 2（请求 1 完成，新请求加入）   │
│  │  2  │  3  │  4  │  5  │                                   │
│  └─────┴─────┴─────┴─────┘                                   │
│  ✅ GPU 利用率更高                                              │
│  ✅ 平均延迟更低                                                │
│  ⚠️ 调度更复杂                                                 │
│                                                                │
│  分块预填充：                                                   │
│  将预填充和解码分成不同批次                                      │
│  预填充批次：[请求 A（1K tokens），请求 B（500 tokens）]        │
│  解码批次：  [请求 C（生成 50），请求 D（生成 120）]            │
│  ✅ 更好的延迟隔离                                              │
│  ✅ 更可预测的性能                                              │
└──────────────────────────────────────────────────────────────┘
```

### 11.5.2 调度算法

| 算法 | 描述 | 最佳场景 |
|------|------|---------|
| **FCFS**（先来先服务） | 简单队列排序 | 低流量系统 |
| **最短作业优先** | 优先处理短请求 | 吞吐量优化 |

| **优先级** | 按请求重要性加权 | 企业 SLA |

## 11.6 成本优化

### 11.6.1 推理成本计算

```
每百万 token 成本 =（GPU 每小时成本 × 小时数）/（生成的 token 数）

70B 模型在云 GPU 上的配置：

配置 A：1 × H100（vLLM，FP16）
  - 吞吐量：~2,000 tokens/sec（batch=32）
  - 每小时成本：~$3.50（云按需）
  - 每百万 token 成本：$3.50 / (2000 × 3600 / 1M) = $0.49

配置 B：1 × H100（vLLM，AWQ INT4）
  - 吞吐量：~4,500 tokens/sec（batch=64）
  - 每小时成本：~$3.50
  - 每百万 token 成本：$3.50 / (4500 × 3600 / 1M) = $0.22

配置 C：1 × A100（vLLM，FP16）
  - 吞吐量：~800 tokens/sec（batch=16）
  - 每小时成本：~$1.50
  - 每百万 token 成本：$1.50 / (800 × 3600 / 1M) = $0.52

配置 D：4 × A100（TensorRT-LLM，FP16，TP=4）
  - 吞吐量：~12,000 tokens/sec（batch=128）
  - 每小时成本：~$6.00
  - 每百万 token 成本：$6.00 / (12000 × 3600 / 1M) = $0.14
```

📌 **真实数据**：OpenAI GPT-4 Turbo 的定价（输入 $10 / 输出 $30 每百万 token）意味着基于估算推理成本 $0.50-$2.00/百万 token，毛利率约为 80-90%。

### 11.6.2 成本降低策略

| 策略 | 成本降低 | 实施难度 | 质量影响 |
|------|---------|---------|---------|
| 量化（INT4） | 2-3 倍 | 低 | 极小 |
| 连续批处理 | 2-4 倍 | 中等 | 无 |
| 模型蒸馏 | 5-10 倍 | 高 | 中等 |
| 投机解码 | 1.5-3 倍 | 中等 | 无 |
| 缓存（语义） | 2-5 倍 | 中等 | 无 |
| 抢占式实例 | 3-10 倍 | 低 | 可靠性风险 |

## 💡 案例研究：Together AI 如何以 10 倍低成本服务 LLM

### 背景

Together AI（together.ai）是一个运行开源 LLM 的云平台。他们以远低于闭源 API 的成本提供 Llama 3、Mixtral 和 Stable Diffusion 等模型的服务。

### 架构选择

1. **多引擎策略**：通用工作负载使用 vLLM，延迟敏感客户使用 TensorRT-LLM，CPU 推理使用 llama.cpp
2. **激进量化**：大多数模型默认使用 AWQ INT4，FP16 作为高级选项
3. **投机解码**：使用小草稿模型（1-3B）加速 70B 模型生成 2-3 倍
4. **动态批处理**：根据流量模式自动调整 batch size
5. **多租户隔离**：PagedAttention 实现租户间安全的显存共享

### 结果

| 指标 | Together AI | OpenAI（GPT-4） | 改进 |
|------|------------|----------------|------|
| 每百万 token 成本 | $0.20-$0.80 | $10-$30 | 10-50 倍便宜 |
| 延迟（TTFT） | 150-300ms | 200-500ms | 相当 |
| 吞吐量 | 3000-8000 tok/s | 仅 API | 更高 |
| 模型多样性 | 100+ 模型 | ~10 模型 | 10 倍更多 |

### 关键要点

1. **开源模型可以匹配闭源质量**：对许多用例而言
2. **量化是规模服务的关键**：成本效益服务必备
3. **多引擎灵活性**：高效服务多样化工作负载
4. **投机解码**：当草稿模型可用时是免费的性能提升

## ⚠️ 战争故事：延迟飙升导致 40% 用户流失

### 背景

一家 SaaS 公司推出了基于微调 Llama 2 70B 模型的 AI 写作助手，通过 vLLM 在 8 × A100 GPU 上服务。初始性能出色：150ms TTFT，35ms token 间延迟，处理 200 个并发用户。

### 事件经过

上线三周后，用户开始抱怨"慢"。监控显示：
- **TTFT**：从 150ms 跳升到 2,000ms+
- **token 间延迟**：从 35ms 增加到 200ms+
- **吞吐量**：从 3,000 降至 500 tokens/sec
- **发生时间**：每天上午 9-11 点（EST）

### 根因分析

1. **流量模式**：市场团队的成功邮件活动将并发用户从 200 增加到 800+
2. **显存压力**：800 个并发会话消耗了 95% 的 GPU 显存用于 KV 缓存
3. **PagedAttention 抖动**：调度器不断将 KV 缓存换入换出，造成巨大开销
4. **无限流**：无论系统负载如何，所有请求都被接受
5. **无自动扩缩容**：8 GPU 集群无法在高峰时段扩容

### 业务影响

- **用户流失**：40% 的免费试用用户在事件第一周内放弃产品
- **收入影响**：估算损失 $20 万年经常性收入
- **品牌损害**：负面社交媒体帖子关于"不可靠的 AI"

### 修复方案

```python
# 1. 每用户限流
class RateLimiter:
    def __init__(self, max_concurrent=5, max_tokens_per_min=10000):
        self.max_concurrent = max_concurrent
        self.max_tokens_per_min = max_tokens_per_min
    
    def check(self, user_id, estimated_tokens):
        # 超过限制则拒绝
        pass

# 2. 动态 batch size 控制
MAX_BATCH_SIZE = 64  # 从 128 减少以留出余量
KV_CACHE_UTILIZATION_THRESHOLD = 0.85  # 85% 时开始降级

# 3. 自动扩缩容触发
def should_scale_up(queue_depth, current_gpus):
    if queue_depth > current_gpus * 10:
        return True
    return False

# 4. 优雅降级
# 压力下切换到更短上下文窗口
# 和更快但能力较弱的模型
```

### 经验教训

1. **始终保留余量**：不要为平均负载规划；为 2-3 倍峰值规划
2. **监控 KV 缓存利用率**：它是性能问题的领先指标
3. **尽早实施限流**：在用户滥用之前保护系统
4. **准备降级模型**：大模型过载时路由到小模型
5. **上线前负载测试**：模拟真实流量模式，而非仅稳态

## 📝 何时使用 / 何时不使用

### 推理引擎选择

| 引擎 | 最佳场景 | 避免场景 |
|------|---------|---------|
| **vLLM** | 通用服务、易用性、社区支持 | 需要 NVIDIA GPU 上的最大吞吐量 |
| **TensorRT-LLM** | NVIDIA GPU 最大性能、大规模生产 | 非 NVIDIA 硬件、需要简单性 |
| **TGI** | HuggingFace 生态集成、简单部署 | 需要前沿功能 |
| **SGLang** | 结构化输出、多轮对话 | 简单单轮推理 |
| **llama.cpp** | CPU 推理、边缘部署、GGUF 模型 | 需要最大 GPU 吞吐量 |
| **LMDeploy** | 中文模型支持、Turbomind 引擎 | 仅英文工作负载 |

### 量化方法选择

| 方法 | 最佳场景 | 避免场景 |
|------|---------|---------|
| **FP16/BF16** | 最高质量、高级选项 | 成本敏感应用 |
| **AWQ INT4** | 通用部署、质量成本平衡 | 需要 INT3 或极端压缩 |
| **GPTQ INT4** | 极端压缩、离线批处理推理 | 在线服务（反量化较慢） |
| **GGUF** | CPU 推理、边缘部署 | 仅 GPU 服务 |
| **FP8** | H100/H200 部署、低比特最高质量 | 非 NVIDIA 硬件 |

### 批处理策略选择

| 策略 | 最佳场景 | 避免场景 |
|------|---------|---------|
| **连续批处理** | 通用生产服务 | 简单离线批处理作业 |
| **静态批处理** | 离线批处理、简单工作负载 | 交互式实时应用 |
| **分块预填充** | 延迟敏感应用 | 仅吞吐量工作负载 |
| **投机解码** | 低延迟需求 | 高吞吐量批处理作业 |
